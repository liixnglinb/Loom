# 修订打磨（ff-refine）

## 本步目标

读 `REVIEW.md` 与 `REVIEW_VERDICT.json`，**逐条修掉** blocker 与 major 问题，
产出 `FINAL.md` 修订说明，并把修坏的风险分析清楚。

这一轮的输入是"别人的意见"，不是"自己的想法"。评审没提的，除非顺手，不要大改。

## 输入

- `REVIEW.md` 问题清单（本步的任务来源）
- `REVIEW_VERDICT.json`
- 被点名的实际产出文件
- `REQUIREMENTS.md`（改完之后回这里对一遍）

## 修订规则

1. **按严重度从高到低处理**：blocker 全清 → major 全清 → minor 挑着做。
   minor 做不动的，移交给最后一步，不要假装做了。
2. **改文件本体，不要只在 `FINAL.md` 里解释**。评审说 `src/app.py` 缺错误处理，
   就去改 `src/app.py`；只写一段"已考虑"等于没改。
3. 每改一处，立刻按 `REVIEW.md` 给的判定依据**复现验证**一次，
   确认问题真的消失了。
4. **守住「已确认无误的部分」**。那些地方是复核明确背书的，除非法条所迫不要碰，
   碰了要说明理由 —— 避免修订轮次里常见的"改回退"。
5. 改动要**成对记录**：`问题编号 → 改了哪个文件哪一处 → 复验结果`。缺一对都算未完成。
6. 若某条 blocker 判定为评审误判，不要硬扛：给出复现证据说明为什么是误判，
   记入 `FINAL.md` 的「不修清单」。评审也可能错，但必须用证据反驳。

## 产出 1：被修订后的实际文件（原地更新）

## 产出 2：FINAL.md

```
# 修订说明

## 修订轮结论
一句话：blocker/major 是否清零，交付是否已达验收标准

## 逐条处置
| 问题编号 | 严重度 | 处置 | 改动位置 | 复验证据 |
| I1 | blocker | 已修 | `src/app.py:42-60` | 跑了 X，输出 Y，问题不再复现 |
| I4 | minor | 移交 | — | 需要用户提供 Z 才能做 |

## 不修清单
| 编号 | 理由（含证据） |

## 连带影响
（本轮改动可能影响到的其他产物/结论，以及是否已同步更新）

## 与验收标准的最终对照
| AC | 标准 | 修订前 | 修订后 |
```

## 硬性规则

- `verdict` 为 `fail` 时，本步必须把全部 blocker 处理完；处理不完就如实写"未清零"，
  并给出剩余阻塞项 —— 绝不允许静默跳过。
- `FINAL.md` 的「逐条处置」必须覆盖 `REVIEW_VERDICT.json` 里每一个 issue id，一个都不能漏。
- 代码型任务：改完必须重新运行一次验证，运行记录进「逐条处置」的证据列。

## 完成前自检

- [ ] 每个 issue id 都有一行处置记录。
- [ ] 被点名的文件确实被改了（用列目录/读文件确认修改时间与内容）。
- [ ] `FINAL.md` 已写入工作区。
