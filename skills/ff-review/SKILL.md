# 自检复核（ff-review）

## 本步目标

**换一副面孔**重看前面所有产出。你不是来确认它做完了的，是来找茬的。
默认立场：它有问题，直到证据说服你。

前序产出是"作者视角"写的，本步要产出"评审视角"的判定。二者冲突时，以证据为准。

## 输入

- `REQUIREMENTS.md` 的验收标准（判定的唯一标尺）
- `PLAN.md` 的任务清单与验证方式
- `EXECUTION.md` 的执行台账
- 工作区里的**实际产出文件**（必须真读真跑，台账说的不算）

## 复核规则

1. **逐条走验收标准**，每条给判定：`通过` / `部分通过` / `不通过` / `无法判定`，
   并附证据（文件:行、命令与输出、数字）。
2. **抽验台账**。台账里声称"已验证"的项，随机抽至少 3 项（不足 3 项则全查）亲自复现。
   复现不出来的，直接定 `blocker` —— 这意味着产出不可信。
3. **专项扫描**六类高发问题：
   - 范围蔓延：做了「明确不做」里的事
   - 覆盖缺口：`PLAN.md` 有任务在交付里查不到对应产出
   - 依据断裂：结论依赖的事实无出处或出处对不上
   - 数字不一致：同一量化事实在不同文件里值不同
   - 只搭骨架：文件存在但内容是占位符/TODO/空函数
   - 静默降级：⚠️ 的偏差被写成 ✅
4. 判定要**可执行**。"建议优化"不算问题；"第 3 节的接口清单缺 `retry` 参数，
   与 `PLAN.md` T2 的约定不符" 才算。
5. 不要在本步动手修。发现问题写清楚，修是下一步的事。

## 产出 1：REVIEW.md

```
# 复核报告

## 结论
一句话：可交付 / 需修订后交付 / 需重做（并说最关键的 1 个理由）

## 验收标准逐条判定
| AC | 标准 | 判定 | 证据 |

## 问题清单
| # | 严重度 | 位置 | 问题 | 判定依据 | 建议修法 |
（严重度：blocker 阻断交付 / major 明显缺陷 / minor 可改进）

## 抽验记录
| 台账项 | 声称 | 实际复现结果 |

## 已确认无误的部分
（明确列出，避免下一步把对的改坏）
```

## 产出 2：REVIEW_VERDICT.json

```json
{
  "verdict": "pass | revise | fail",
  "blocker": 0,
  "major": 0,
  "minor": 0,
  "ac_total": 0,
  "ac_passed": 0,
  "issues": [{"id": "I1", "severity": "major", "where": "文件:位置", "what": "一句话", "fix_hint": "一句话"}]
}
```

`verdict` 规则：有任一 `blocker` → `fail`；无 blocker 但有 major → `revise`；
仅 minor 或全通过 → `pass`。

## 硬性规则

- 两个文件都必须真实落盘。`REVIEW_VERDICT.json` 必须是合法 JSON（不含注释）。
- 问题清单为空时，必须在「已确认无误的部分」列出逐条证据，说明真的查过了。
- 每条判定都要有证据；"看起来没问题" 不是证据。

## 完成前自检

- [ ] 每条验收标准都有判定与证据。
- [ ] `REVIEW_VERDICT.json` 能被 JSON 解析器读通，计数与问题清单一致。
