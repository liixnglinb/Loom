# 逐项执行（ff-execution）

## 本步目标

把 `PLAN.md` 里的任务清单**逐条做完**，产出物真实落到工作区，
并在 `EXECUTION.md` 里留下一条可核对的执行台账。

这一步是整个工作流的重心。前面几步都是铺垫，后面几步都是校验它。

## 输入

- `PLAN.md`（任务清单、执行顺序、验证方式）
- `FINDINGS.md`（事实、可复用资产、缺口）
- `REQUIREMENTS.md`（验收标准，最终判定依据）

## 执行规则

1. **按执行顺序做，一条一条来**。做完一条立刻验证该条的"验证方式"，验证不通过就地修，
   不要带着未修的坑继续往下走。
2. **产出物必须是真文件**。要 `src/app.py` 就写出 `src/app.py`，
   不要在台账里贴代码片段代替落盘。代码型任务的每个文件写完后必须实际运行一次。
3. **不许伪造结果**。没跑过的命令不要写"输出正常"；没读过的文件不要写结论。
   做不到、跑不通的，如实写进「偏差」。伪造比失败严重得多。
4. 长耗时操作（编译、训练、批量处理）留在本回合内跑完并等到结果，
   不要挂后台就结束 —— 后台进程会随会话结束被中断，产出是空的。
5. 改到已有文件时保留原有功能，破坏性改动写进「偏差」并说明理由。
6. 每条任务的台账必须包含**证据**：文件路径、命令、输出摘要、数字。
   形容词不算证据。

## 产出

1. **各任务的实际产出物**（`PLAN.md` 指定的路径，原样落盘）。
2. **EXECUTION.md** 执行台账：

```
# 执行台账

## 总览
| # | 任务 | 状态 | 产出物 | 验证结果 |
| T1 | … | ✅完成 / ⚠️降级 / ❌未完成 | `path` | 跑了 X，得到 Y |

## 逐条记录
### T1 …
- 做了什么：
- 产出：`路径`
- 验证：命令 → 输出摘要
- 遗留：

## 偏差与决策
| 计划 | 实际 | 原因 | 影响 |

## 数字汇总
（把交付里出现的量化结果集中列一遍：多少文件、多少行、跑了几轮、准确率多少…）

## 未完成
（若全完成，写"无"）
```

## 硬性规则

- `PLAN.md` 的每个任务在台账里都必须有一行，一个都不能漏。状态只能三选一。
- 状态为 ⚠️/❌ 的任务，必须写清原因与影响。
- 代码型任务：所有 `.py` / `.js` / `.ts` 等可执行文件必须有实际运行记录（或说明为何不可运行）。

## 完成前自检

- [ ] 逐条对照台账与 `PLAN.md`：任务数一致，产出物文件确实存在（用列目录确认，不是凭记忆）。
- [ ] 台账里没有任何"应该/大概/预期"这类没验证的措辞。
- [ ] `EXECUTION.md` 已写入工作区。
