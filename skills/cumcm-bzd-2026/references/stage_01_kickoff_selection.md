# Stage 1 · 启动与选题

> 本阶段由十阶段版的 Stage 0（团队启动与资料预扫）与 Stage 1（多题比较与选题）合并而成。
> 合并理由：环境预检与规则基线是选题的**前置条件**，不是独立任务。拆成两个阶段会让团队在工具链未就绪的情况下先花 1 小时"启动"，再花 2–4 小时选题，中间产生一次无意义的状态写入。

## 目标

在开工前把四件事定死：**谁能做什么、工具是否可用、当届规则是什么、选哪道题**。

这四件定不死，后面每个阶段都会返工。

## 时长

3–5 小时（含选题比较）。题面未公布时只完成前半段，保持 `qi_count=null` 等待。

## 输入

- 赛题与附件路径（或"未公布"）
- 队员数与各人擅长
- 截止时间
- 环境：`python scripts/doctor.py` 的输出

## 执行步骤

### 步骤 1 · 环境预检（约 15 分钟）

```bash
python <wf>/scripts/doctor.py --workspace <cwd>
```

检查 Python、Pandoc、TeX 引擎、科学计算栈与工作区结构。**不通过不进下一步** —— 临近提交才发现编译器缺失是典型的时间灾难。

记录 `tools_ready` 与未通过项的应对方案（降级 / 安装 / 换人负责）。

### 步骤 2 · 角色与协作约定

明确三件事，写入 `team_roles`：

| 项 | 内容 |
|---|---|
| 负责人 | 每个阶段谁拍板 |
| 复核人 | 谁检查产物（不能与负责人同一人） |
| 交接产物 | 交给下一阶段的文件路径 |

角色可随阶段变化：建模阶段建模手主导，写作阶段写作手主导。**避免"三人都全栈但都不深"** —— 这会让每个判断都缺少明确的负责主体。

同时约定：统一种子记录方式、符号命名规则、文件命名规则。

### 步骤 3 · 规则基线核对

读 `references/rules_baseline.md`，打开其中的官方链接核对**当届**通知，至少确认：

- 页数限制与起始页
- 匿名要求（哪些位置不能出现身份信息）
- 承诺书与编号页要求
- 是否需要目录（国赛明确不要）
- 支撑材料与 AI 使用披露的形式要求

写入 `compliance.ruleset`，含 `verified_at` 与 `official_urls`。

**仓库基线不能替代当届通知。** 规则每年都可能变，本阶段、Stage 8、Stage 9 各核对一次（规则核对三重门 · 第 1 道）。

### 步骤 4 · 资料预扫

对每道候选题做快速扫描（每道 20–30 分钟），记录 `problem_scan`：

| 项 | 关注点 |
|---|---|
| 数据规模与结构 | 是否有附件、量级、是否含时序/空间/网络结构 |
| 附件可用性 | 能否打开、字段是否自解释、缺失与异常比例 |
| 子问数量与耦合 | 几问、后问是否依赖前问结果 |
| 学科门槛 | 是否需要本队不具备的领域知识 |
| 开放性 | 是否有明确评判口径，还是"自圆其说"型 |

### 步骤 5 · 多题比较与选题

对每道候选题，从四个维度打分（1–10）：

1. **资源匹配**：现有数据与方法能否支撑
2. **团队能力匹配**：是否落在队伍擅长区间
3. **区分度**：做出差异化结果的空间有多大
4. **失败风险**：做不出来或做成流水账的概率

选题决策必须写出：

- `selected`：选定题号
- `rationale`：为什么选它（引用上面四个维度的实际打分）
- `rejected_alternatives`：放弃了什么、**为什么**（这条比选题理由更重要，它防止中途摇摆）
- `risks_identified`：已知风险与应对

**选题摇摆是 Stage 1 的典型失败模式。** 一旦选定，改题需要新证据触发，并在 `events` 中记录触发条件。

### 步骤 6 · 判定 task_type

根据题面特征写入 `task_type`，用于后续查 `config/dim_weights.json`：

| 特征 | task_type |
|---|---|
| 求最优方案、路径、排程、配比 | `optimization` |
| 分类、判别、评级、打分 | `classification` |
| 预测未来值、外推 | `prediction` |
| 多方案/多指标排序选优 | `decision` |
| 机理演化、微分方程、仿真 | `simulation` |
| 统计推断、相关性、显著性 | `statistics` |
| 网络结构、图关系 | `graph` |
| 信号、周期、频谱 | `signal` |

`task_type` 决定后续各阶段的评分权重。选错会让加权分数失真。

## 产物

`<cwd>/state/decision_log.json` 的 `stages.1` 节点：

```
team_roles          负责人 / 复核人 / 交接产物
tools_ready         预检通过项与未通过项的应对
problem_scan        每题的扫描结果
candidates_assessed 候选评估
selected            选题
rationale           理由
rejected_alternatives 放弃项及原因
risks_identified   风险
time_budget_h      各阶段时间分配
```

以及 root 层的 `task_type`、`compliance.ruleset`、`problem_meta`。

## 5 维评分

| 维度 | 判据 |
|---|---|
| `1_resource_fit` | 数据与工具能否支撑，缺什么、能否补 |
| `2_capability_fit` | 是否落在队伍能力区间 |
| `3_risk_identified` | 是否识别了真实风险（不是"时间紧"这类废话） |
| `4_rule_baseline` | 当届规则是否核对、是否有据可查 |
| `5_decision_quality` | 选题与放弃项是否有可核验的论证 |

## 检查清单

- [ ] 环境预检通过，或有明确的降级方案
- [ ] 每个阶段有负责人与复核人，且非同一人
- [ ] 当届官方通知已打开核对，链接已记录
- [ ] 每道候选题都扫过，不是"听说 C 题简单"
- [ ] 放弃项写明了原因
- [ ] `task_type` 已判定
- [ ] 时间预算按 9 个阶段分配，且给 Stage 8 留了足够余量
- [ ] 风险清单不含"时间有限、能力不足"这类无效条目

## 退出条件

- `verdict = pass`（raw_min ≥ 7 且 weighted_mean ≥ 8），或
- `verdict = carryover`（迭代 3 次仍未达标，带标记进入 Stage 2）

题面未公布时：完成步骤 1–3，`current_stage` 保持 1，等待题面。
