# 交付整合（ff-delivery）

## 本步目标

前面几步产出的是"给流程看的文件"（台账、复核、修订说明）。
本步产出**给人看的交付物**：使用者打开就能明白"我得到了什么、怎么用、还差什么"。

读者假设：他只看了你这一份文件，没看过程。

## 输入

- 工作区全部产出文件（先 `ls` 确认实际存在，不要凭前序文件的描述）
- `REQUIREMENTS.md`（验收标准）、`FINAL.md`（遗留与移交项）

## 整合规则

1. **只汇总，不新增结论**。本步不做新判断、不改任何前序产出。
   发现前面有错，如实写进「已知问题」，不要偷偷改 —— 改了就没有依据了。
2. 每一项交付物都要给：**是什么、在哪、怎么验证它是对的**。
   路径必须逐字核对存在，写一个不存在的路径是本步最严重的错误。
3. 面向读者的第一屏放结论，不放过程。先答"结果是什么"，再答"怎么来的"。
4. 使用说明要能照着敲。代码型给安装与启动命令，文档型给阅读顺序，
   分析型给关键数字与结论出处。
5. 「遗留事项」必须诚实。移交清单、待核实事实、未通过的验收标准，
   一条都别藏 —— 使用者据此决定下一步动作。

## 产出：DELIVERABLE.md

```
# 交付说明

## 结论摘要
（3–6 句：做成了什么，达到什么效果，最关键的一个数字或产出）

## 交付物清单
| # | 名称 | 路径 | 类型 | 对应验收标准 | 如何验证 |

## 使用方式
（照做即可跑通的步骤 / 阅读顺序）

## 关键结论与依据
| 结论 | 依据（文件:位置 或 数字） | 置信度 |

## 验收标准达成情况
| AC | 标准 | 状态 | 说明 |

## 已知问题与遗留
| # | 事项 | 严重度 | 建议下一步 |

## 过程索引
（REQUIREMENTS / PLAN / FINDINGS / EXECUTION / REVIEW / FINAL 各自的一句话摘要，供追溯）
```

## 硬性规则

- 「交付物清单」的每条路径，本回合内必须实际确认存在（列目录核对）。
- 「验收标准达成情况」逐条给状态，与 `FINAL.md` 的对照表不得矛盾；
  有矛盾时以实际文件为准，并把矛盾写进「已知问题」。
- 不得出现"详见上文"却无出处。所有引用落到具体文件路径。

## 完成前自检

- [ ] 清单里每个路径都验证过存在。
- [ ] 只读这一份文件的人，能说出自己拿到了什么、怎么用。
- [ ] `DELIVERABLE.md` 已写入工作区。
